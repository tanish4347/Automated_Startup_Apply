# Fixed Product Architecture

The architecture and product behavior below are fixed. Claude should choose all implementation details beyond this architecture.

```text
                 JOB SOURCES
                     ↓
              JOB ACQUISITION
                     ↓
              JOB NORMALIZATION
                     ↓
              DEDUPLICATION
                     ↓
                  JOB DB
                     ↓
             APPLICATION QUEUE
                     ↓
          APPLICATION AUTOMATION
                     ↓
             APPLICATION DB
                     ↓
              STATUS TRACKING
                     ↓
                 DASHBOARD
                     ↓
      INTERVIEW / ASSESSMENT PREPARATION
```

A separate candidate-profile / answer store feeds the application engine:

```text
CANDIDATE PROFILE / ANSWER STORE
              ↓
        APPLICATION ENGINE
```

## Fixed Product Requirements

- No eligibility filtering.
- No AI deciding whether a job is worth applying to.
- The system should attempt to apply to as many discovered jobs as technically possible.
- Store the full job information and a snapshot of the job at application time.
- Store useful company information.
- Store exactly what was submitted: resume, answers, application URL, date, status, etc.
- No email-monitoring system.
- For uncertain or blocked application steps, use the safest practical mechanism Claude determines appropriate.
- The UI should make it easy to understand what was applied to, what the company does, what the role was, what was submitted, and what happened next.
- Do not bypass CAPTCHAs, authentication protections, anti-bot controls, or platform restrictions.
- Where direct automation is unsuitable, choose the best practical compliant alternative.
- Claude decides the exact scraper, APIs, browser automation framework, storage model, queue implementation, ATS handling, libraries, etc.

# Prompt 1 — Build the Foundation

You are the lead software architect and senior engineer for this project.

I want you to build a personal automated job-application system.

IMPORTANT: I am deliberately giving you the PRODUCT ARCHITECTURE, not the implementation choices. You should make the engineering decisions yourself. Research current tools, APIs, platform constraints, browser automation options, databases, queues, and other technologies where necessary, and choose the most reliable practical solution.

Do not ask me to choose between technical alternatives unless you are genuinely blocked. Make the decision yourself and implement it.

CORE PRODUCT GOAL:

The system should discover as many relevant off-campus job opportunities as technically possible across multiple job sources, store all useful information about each opportunity, and attempt to apply to as many of them as technically possible.

There is NO eligibility filtering.

The system must NOT decide:
- whether I am qualified
- whether my degree is appropriate
- whether my college is appropriate
- whether the role is a good fit
- whether I personally should apply

Every discovered job should enter the system unless it is a duplicate, clearly unavailable/closed, or technically impossible to process.

FIXED HIGH-LEVEL ARCHITECTURE:

JOB SOURCES

JOB NORMALIZATION

    ↓
APPLICATION AUTOMATION
    ↓
APPLICATION DATABASE
    ↓
STATUS TRACKING
    ↓
DASHBOARD
    ↓
INTERVIEW / ASSESSMENT PREPARATION

A separate candidate-profile / answer store feeds the application engine.

The system must store:
- full job description
- responsibilities
- requirements
- preferred qualifications
- company
- role
- location
- work mode
- compensation if available
- posting date if available
- deadline if available
- source
